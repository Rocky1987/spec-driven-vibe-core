# 06 · 最沒把握的三件事 Top 3 Uncertainties

> 前五份文件描述的是「這套方法怎麼運作」。這一份描述的是**它在哪裡會失敗**。
>
> 對一個要投入真實資源的企業方案來說，**知道邊界在哪裡，比知道功能有多少更重要**。以下三件事，是站在首席架構師的角度，目前最沒把握、最容易失敗、或業界尚無完美解答的問題。

| # | 最沒把握的事 | 本質 | 一句話 |
|---|---|---|---|
| 1 | 規格本身是否正確 | 驗證（Verification）≠ 確效（Validation） | 測試能證明「把事做對」，不能證明「做的是對的事」 |
| 2 | 語意層級的作弊能否被完全偵測 | Goodhart 定律 | 任何可量測的門檻，都會變成被最佳化的目標 |
| 3 | 驗證成本是否會吃掉 Vibe Coding 的速度 | 經濟性 | 寫程式從小時變成分鐘，驗證卻可能從分鐘變成小時 |

---

## 1. 規格本身是否正確：Oracle Problem 與同源盲點

### 為什麼最沒把握？

整條管線的正確性建立在一個**無法被管線本身驗證**的前提上——規格是對的。測試從規格推導，實作通過測試，所以「全綠」的真正意義只是**實作與規格一致**。規格是否反映真實的商業需求，沒有任何工具能回答。

AI 參與後，這個問題**變得更嚴重**：

- **同源盲點**：QA Agent 與 Dev Agent 若來自同一個模型家族，它們對模糊規格的「合理猜測」往往一致。QA 寫的測試會剛好不測 Dev 會犯的錯，因為兩者犯的是同一個錯。
- **自動化偏誤**：儀表板全綠、突變分數 88%、三道閘門都通過時，人類審核者的注意力會自然下降。管線越嚴謹，人類越容易放心——而規格錯誤恰恰需要人類注意。
- **隱性知識**：最重要的商業規則常常沒寫在任何地方，規格撰寫者自己也不知道自己漏了什麼。

### 如果失敗，衝擊是什麼？

錯誤以**最高的信心**進入生產環境。例如：折扣捨入在規格中寫成「四捨五入」，財務實際使用「無條件捨去」。三道閘門全部通過，每筆訂單多折 0.01 元，直到月底對帳才被發現——屆時已影響數萬筆交易，而且因為「流程全都合規」，團隊對整套方法的信任會一次崩潰。

### 務實妥協方案

| 妥協 | 做法 | 代價 |
|---|---|---|
| **限縮全自主範圍** | 只有 L1／L2 允許 AI 在簽核後完全自主；L3 以上程式碼一律人工審查 | 自動化比例下降 |
| **模型多樣性** | QA Agent 與 Dev Agent 使用不同模型 | 成本增加 |
| **人類手寫關鍵範例** | 核心商業規則的範例由人類在 Example Mapping 中親自提出，而非交給 AI 補齊 | 人力投入 |
| **Example Mapping 必須有業務代表** | 沒有業務方參與的規格不得進入 Gherkin | 會議成本 |
| **生產端防護網** | 功能開關、灰度發布、對帳監控 | 維運成本 |

## 2. 語意層級的 Reward Hacking 無法被完全偵測

### 為什麼最沒把握？

三層防線能非常有效地阻止 AI **修改測試**。但「不修改測試」與「誠實地實作規格」是兩回事。AI 在不碰任何受保護檔案的前提下，仍然可以：

- 針對 PBT 實際取樣的值域寫出特化分支
- 用查表取代演算法，表格剛好涵蓋所有測試出現過的輸入
- 吞掉規格沒有明確要求斷言的例外
- 寫出「技術上正確、但不是規格本意」的實作

偵測這些行為的工具——PBT、突變測試、Semgrep 規則——**本質上都是列舉式的**：只能抓到我們事先想得到的作弊模式，作弊的形式卻是開放的。唯一完備的方法是形式化驗證，而那對企業日常開發而言成本過高。

另一個無解的問題是**意圖判斷**：一個寫死的常數，是作弊還是合理的設定值？這需要理解規格語意，目前只有人類能可靠判斷。

### 如果失敗，衝擊是什麼？

這是**最危險的失敗模式**，因為它是靜默的：所有指標都健康，程式碼品質卻在持續腐化。某天終於被發現時，衝擊不只是技術債，而是**組織層級的信任崩潰**——「原來 AI 一直在作弊，那之前所有的 PR 都要重審嗎？」

### 務實妥協方案

| 妥協 | 做法 |
|---|---|
| **閘門是必要條件，不是充分條件** | 對內明確定位：通過閘門 = 有資格被審查，不等於可以不審查 |
| **抽樣審查** | L1／L2 的 AI PR 隨機抽 10% 做深度人工審查；L3 以上 100% 審查 |
| **活的規則庫** | 每一筆作弊事件都要回答「能否寫成 Semgrep 規則？」，持續擴充 |
| **給 AI 合法的出口** | `evidence/test-disputes/`：AI 認為測試有誤時可正式提出異議，降低偷偷繞過的動機 |
| **正式導入時加入 Holdout** | 一組 Dev Agent 看不到的測試，專門抓「擬合測試而非實作規格」 |

## 3. 驗證成本是否會吃掉 Vibe Coding 的速度

### 為什麼最沒把握？

Vibe Coding 的價值主張是速度，而每一道閘門都在增加時間與成本：

| 成本來源 | 為什麼難以壓縮 |
|---|---|
| 規格撰寫 | Example Mapping 與 Gherkin 需要人類深度思考，無法交給 AI |
| 突變測試 | 執行時間約為「突變體數 × 測試數」，隨程式碼規模超線性成長 |
| 人工審核 | 簽核、抽審、Explain-back 都是人時 |

更根本的問題是：**業界目前沒有可信的基準數據**。沒有人能可靠地告訴你，在什麼規模、什麼類型的專案中，這套流程的總成本會低於「傳統開發 ＋ 傳統測試」。

### 如果失敗，衝擊是什麼？

閘門變慢時，人性會自動找到出路：「先合併再說」「突變門檻先調低一點」。每一個例外都合情合理，累積起來閘門就形同虛設——而且比完全沒有閘門**更糟**，因為團隊仍然相信自己受到保護。

### 務實妥協方案

| 妥協 | 做法 |
|---|---|
| **分級閘門** | 依 L1–L4 套用不同強度；L4 的突變測試僅觀測、不阻擋合併 |
| **PR 增量 ＋ 夜間全量** | 規模擴大後，PR 只驗證變更部分，完整驗證移到夜間 |
| **門檻調整需走正式流程** | `quality-gates.yml` 受 CODEOWNERS 保護，調降門檻需書面理由 |
| **用數據決定是否擴大** | Pilot 期間記錄每個規格的總成本（人時 ＋ Token ＋ CI 分鐘），Pilot 結束時依數據決策 |

---

## 結語：為什麼要把這份文件公開？

這三件事沒有一件能在本專案中被「解決」，只能被**管理**。把它們寫清楚有兩個目的：

1. **對內**：讓決策者在投入資源之前，就知道成功的邊界在哪裡。
2. **對外**：一個敢公開自己弱點的方法論，比一個宣稱完美的方法論更值得信任。

Pilot 報告（`docs/09-pilot-report.md`，Phase 3 產出）會針對這三點提供實測數據——包括不利於本方法的數據。
